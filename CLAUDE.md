# Launcher agent guide

## What this repository is

This Go repository builds one Windows executable,
`dist/Sacred Mod Loader.exe`. A player puts it in the Sacred Gold folder and
runs it. The executable contains the loader, installs that payload in the game
folder, presents mods and hook sites in WebView2, saves every choice, starts the
host, and then starts the game.

The launcher is a player-facing application. No other repository imports it.

## Where things are

| Path | What it owns |
|---|---|
| `main.go` | Wiring only: find the game, unpack, load conf, build `ui.State`, run the window. |
| `console.go` | `AllocConsole` for the `--debug` console and the console-mode fix below. |
| `install/` | The embedded payload (`//go:embed all:payload`), finding the game folder, unpacking, the version check. |
| `install/payload/` | Staged by `tools/build.ps1`. Only `.gitkeep` is tracked. |
| `conf/` | `launcher.json`, which stores the player's last choices. |
| `hooks/` | Reads hook site names out of the agent scripts in the game folder. |
| `mods/` | Reads `META-INF/declaration.toml` out of each jar in `<game>/mods`, without a JVM. Owns `API`, the loader contract, and answers `Loader.Refuse`. |
| `pin/` | The version notation a descriptor pins with: Maven-style ranges, the ones NeoForge writes. Nothing else in here parses a version. |
| `registry/` | Where mods come from. Resolves a clone URL to a file URL, reads an SRML index, decides what to offer, downloads and installs, and holds the icons. `work.go` is the async half the page polls. |
| `fetch/` | One HTTP download, done the same way by the JDK fetcher and by the registry: progress, hashing, and nothing partial left behind. |
| `secret/` | DPAPI. A token for a private mod repository is encrypted with the player's Windows account when DPAPI works. The UI warns when it will be saved as plain text instead. |
| `game/` | Starts `protocol.exe`, then the game, and waits. `exe.go` owns the executable names, the build the addresses came from, and reading the one in the folder. |
| `java/` | Finds the JDK the host will run Coderpack on, and fetches one from the foojay Disco API when the machine has none. |
| `ui/` | The WebView2 window. `ui/web/` is inlined into one HTML string. |
| `ui/dpi.go` | DPI awareness, declared before any window exists. |
| `tools/` | `build.ps1` (payload + binary), `install.ps1` (build + copy into the game folder), `rsrc/` (the Windows resources: icon and version block). |

## The payload

`install/payload` is generated output, not source. `tools/build.ps1` deletes it,
stages dependencies from sibling checkouts or pinned releases, and lets
`go build` embed the result. Files under `payload/` unpack to
`<game>/launcher/...`. If a future payload contains `payload/mods/*`, those
files unpack to `<game>/mods/...`.

    payload/VERSION          copied to <game>/launcher/VERSION
    payload/protocol.exe     the host, from ../protocol (cargo build --release)
    payload/api.jar          from ../coderpack (gradlew jar)
    payload/zygote.jar       from ../coderpack
    payload/agent/*.js       from ../coderpack/agent/src, in file-name order
    payload/agent/gen/addr.js  generated during the build, see below
    (no payload/mods)        this launcher ships no mod

On the from-source path `addr.js` is generated by the build (`python
tools/addr.py <mappings>` run inside the coderpack checkout), never taken from a
checkout. A stale address table is a hook that silently never fires, so the
payload cannot ship an old one.

Without the siblings the build downloads instead of failing. `dependencies.json`
pins one release tag per repository (`{ "path": "ancaria-dev/protocol", "version": "0.99.0" }`
and the same shape for `coderpack`) and
`Fetch` pulls `protocol.exe`, `api.jar`, `zygote.jar` and `agent.zip` from
`https://github.com/ancaria-dev/<repo>/releases/download/v<tag>/<file>`, with no
token, because these are public releases. `agent.zip` already carries
`gen/addr.js`, so that path needs neither Python nor a mappings checkout and Go
is the only tool required. `-Protocol none` and `-Coderpack none` force it even
when a checkout is there. Either way the build stops unless
`payload/agent/gen/addr.js` exists afterwards.

No mod jar is staged. Mods are installed at run time from a repository the
player can see and choose from, so the launcher does not carry somebody else's
choices and does not grow by nine megabytes when a mod packs a UI toolkit.

`Unpack` creates `<game>/mods` directly. `go:embed` stores files, so an empty
`payload/mods/` directory would not survive embedding. The directory is created
before the version check on every run, including runs that do not upgrade the
payload.

`Unpack` runs only when `<game>/launcher/VERSION` differs from the embedded one.
It writes files, never replaces a directory, and skips names starting with `.`.
A file it cannot overwrite (a running executable) is renamed to `<name>.old` first.

## What Windows is told about the file

The executable's `.rsrc` section contains the icon used by Explorer and the
taskbar, plus the version block shown on the Details tab of the Properties
dialog. Windows reads both before the program runs.

`tools/rsrc` writes both into `rsrc_windows_amd64.syso`, which `go build` links
in by name out of the module root, and `build.ps1` runs it before every build.
Written here rather than taken from `go-winres` or `rsrc` because CI builds this
repository with nothing installed but Go, and a resource compiler resolved from
the network is a build that stops working on the day that download does. What it
emits is a COFF object with one section and a handful of relocations.

Its two inputs are tracked, while its output is generated.
`tools/rsrc/sacred.ico` is cut from `sacred.png` by `tools/rsrc/icon.py` at ten
sizes from 16 through 256. `.version` also stamps the embedded payload, which
keeps the Properties dialog and the page title on the same version.
`ui/web/icon.png` comes from the same script and is embedded as a data URI for
the header and for mods without their own image.

Both failure modes here are silent, which is why `tools/rsrc` is the one tool in
this repository with unit tests. A version block whose padding is measured from
the wrong place still links and still sits at the right type and id, and Windows
then answers every question about the file with an empty string. A group icon
written with the wrong stride does the same and leaves the file drawn with Go's
default icon. Neither produces an error anywhere.

## Java

Mods are Java. The host starts them in a JVM of its own next to the game, so a
player with no JDK gets a launcher that works, a game that starts and not one
mod loaded. That used to be silence. `java/` turns it into a sentence above the
Play button and a way out.

`java.Find` looks in three places and takes the first one new enough for the
zygote, which wants 21:

    <game>/launcher/java     a JDK this launcher downloaded
    $JAVA_HOME/bin/java.exe
    java on PATH

The order is a preference and not an override. A downloaded Java 17 does not
shadow a system Java 21. The search keeps going and comes back with the one
that can actually run. When nothing is new enough, the first Java it found still
comes back, so the page can say "Java 17 from PATH, and the loader needs 21"
instead of the useless "no Java". Which copy won is written above Play in every
case, because a player debugging a mod against the wrong JVM has no way of
guessing that is what they are doing.

The version comes out of the JDK's own `release` file, one line reading
`JAVA_VERSION="25.0.4"`. No process is started for it. Only a `java` on PATH
belonging to something that is not laid out like a JDK falls through to running
`java -version` and reading stderr.

`disco.go` queries `https://api.foojay.io/disco/v3.0/`, the discovery service
used by javaalmanac.io. Both dropdowns come from that API. Distributions are
selected by rule: they must be maintained, available, and OpenJDK builds.
GraalVM-derived entries stay out because they are a different product. Versions
are maintained GA releases from 21 onward.

The page defaults to Oracle and Java 25. Do not assume that a default or any
other vendor and version pair remains downloadable. `Resolve` asks the live
service for a Windows package and distinguishes an unavailable build from one
that requires a browser download.

Then `get.go` streams it into `<game>/launcher/java.part`, hashing as it goes.
When foojay publishes a SHA-256 digest, the launcher compares the download
against it. It then unpacks into `java.new` and swaps that over `java` at the
very end. A download that disagrees with its checksum is deleted rather than
kept. A run that dies halfway leaves the JDK that was already working still
working, and `java.Sweep` clears the leftovers at the next start.

Whatever wins is passed to the host as `--java <path>`. The flag was already
there and `game.Start` now fills it in. `protocol.exe` on its own prefers
`<install>/java/bin/java.exe` before `JAVA_HOME`, so a host started by hand out
of the game folder reaches the same JVM the launcher would have handed it.

## Mods

The page has two mod tabs. Installed lists the jars already in `<game>/mods`
through `mods.Scan`. Available lists candidates returned by configured
repositories.

A **remote** is a git repository with `sacred.mods.repository.json` at its root.
Nothing here runs git. The clone URL is an address and `registry.Candidates`
turns it into the address of that one file: GitHub has two shapes (the raw host,
and the API for a private repository, which the raw host will not serve with a
token), and everything else is tried against the GitLab shape and then the two
Gitea ones. Whichever answers with a readable index is remembered in
`Remote.Raw` as a template with `{path}` in it, so the misses are paid for once.
`Normalize` requires `https://` and a `.git` suffix. The suffix is a
deliberate gate, not a technical need, and it is the difference between an
address somebody meant to paste and whatever was in the clipboard.

`registry.Official` is the default and it is a list, because a second one is a
partner rather than a rewrite. A player's own remotes live in `conf.Remotes`.
The official one cannot be removed: a launcher with no repositories is a page
with nothing on it and no way back.

`Merge` decides what is offered, and its rule about conflicts is blunt on
purpose. Two mods that rewrite the same thing produce whichever answer the
loader asked for last, and no player can be expected to know that, so **both
sides leave the list**. That covers a mod naming another in its descriptor's
`conflicts`, either side of that pair already being installed, and the same id
coming from two repositories at once, which is its own ambiguity: there would be
no saying which one Install meant. A mod already installed is never offered, and
one whose version differs from the offered one gets an Update button rather than
a second row.

`Install` performs three independent checks before a jar may remain. Its
SHA-256 must match the index. The mod ID in its descriptor must match the
offered ID. Its `api` and `loader` ranges must accept this launcher. The ranges
are read from the jar, not trusted from the index, because the loader reads the
jar's descriptor.

The installed file name is built from the id and version after both have passed
character-level validation. A network value never chooses a local path. An
update removes the old jar before the new one lands, so the folder never holds
two versions of one mod.

Icons reach the page as data URIs. The window is loaded from a string and has no
origin, so a `file://` path resolves to nothing. Icons are capped at 256 KB and
requested one at a time. `encode` sniffs the bytes and rejects anything that is
not an image, including SVG because it is a scriptable document. The cache is
keyed by mod id, allowing an installed mod to keep its image while its
repository is unavailable.

Tokens pass through `secret`. DPAPI binds an encrypted value to the logged-in
Windows user and machine without storing another unlock key. Code running as
the same user can still decrypt it, so DPAPI is not a vault. It prevents a
credential from remaining readable in a copied game folder. `secret.Seal`
falls back to plain text when protection fails. `secret.Works()` is checked at
startup, and the page states whether a token will be encrypted or saved as
plain text.

Slow registry work runs in a goroutine because WebView2 bindings run on the
window's message thread. The page polls `Work.View`, permits one registry job at
a time, and redraws only when the result changes. This keeps the window
responsive and prevents a list from rebuilding under the pointer.

## Build, install, test

The isolated build needs Go 1.26. Building sibling dependencies from source
also needs JDK 21, Python 3.11, and Rust 1.98 with the MSVC toolchain and LLVM.
`frida-sys` runs bindgen, which needs libclang.

    pwsh tools/build.ps1          # stage payload, then go build -ldflags -H=windowsgui
    pwsh tools/build.ps1 -Bump    # same, after raising the patch number in .version
    pwsh tools/install.ps1        # build, then copy the exe into the game folder
    pwsh tools/install.ps1 -Bump  # -Bump is forwarded to build.ps1

    go vet ./...
    go test ./... -count=1

`build.ps1` also takes `-Protocol`, `-Coderpack`, `-Mappings` to point at
checkouts that are not siblings. `none` as the value of the first two forces the
download path described above.

CI runs for pull requests, manual dispatches, and pushes to `master`. It builds
through the dependency download path, then runs `go vet ./...` and
`go test ./... -count=1`. On `master`, including a manual dispatch there, it
publishes only when `.version` has no `v<version>` tag on the remote. The
release contains `dist/Sacred Mod Loader.exe` and creates that tag. `-Bump`
raises the number, and raising it is what makes a new release eligible.
`tools/version.ps1` does the same edit directly: no argument prints the
current version, `pwsh tools/version.ps1 0.99.1` writes a specific one. It
never touches `dependencies.json` -- that pins `protocol` and `coderpack`,
not this repository.

`install.ps1` reads the game path from `.local.settings`, which is not committed
because every machine has Sacred Gold somewhere else. One line:

    sacred=D:\SteamLibrary\steamapps\common\Sacred Gold

Run the build before the test. `hooks/hooks_test.go` reads the shipping agent
from `../install/payload/agent` and calls `t.Skip` when the payload is absent. A
green test run on a clean checkout has not exercised staged-agent scanning.

Tests under `java/` and `registry/` do not contact external services. Registry
tests serve an index, a test-built jar, and an icon from `httptest` over TLS.
`fetch.Transport` points the production path at that server, so the test still
parses the index, downloads and hashes the jar, opens its descriptor, and checks
the installed file. `TestResolveTriesEveryShapeUntilOneAnswers` serves only the
Gitea shape and catches code that stops after the first miss.

Java API tests parse verbatim service responses stored under `java/testdata`.
Download tests use loopback `httptest` servers. When a foojay response shape
changes, save a fresh response instead of editing a fixture by hand:

    curl "https://api.foojay.io/disco/v3.0/distributions?include_versions=false&include_synonyms=false" -o java/testdata/distributions.json

## Rules

- Do not add a hand-written table of hook names. `hooks.Scan` matches
  `name("...", RVA.…)` in the agent scripts so a new site cannot be missing from
  the list, and a site nobody can see is a site nobody can switch off.
- Do not edit anything under `install/payload/`. The next build deletes it.
- Do not stage a mod into the payload. Mods come from a repository at run time,
  and a mod shipped inside the launcher is a mod the player did not choose and
  cannot remove for good.
- Nothing off the network decides a path. A mod's file name is built from its id
  and its version after both have been checked, an icon's cache name is its id,
  and `safePath` throws away anything with `..`, a leading slash or a backslash
  in it before it is appended to a URL. The index is somebody else's file.
- A downloaded jar is not installed until its SHA-256 matches, its own
  descriptor's mod ID matches the offered ID, and its own `api` and `loader`
  ranges cover this launcher. Removing any of those three leaves a different
  lie unchecked.
- Keep token storage and the sentence under the field aligned. `secret.Seal`
  uses DPAPI when protection works and falls back to plain text when it fails.
  `secret.Works()` decides which outcome the page announces at startup.
- `conf.OffHooks` stores what is OFF, not what is on. Keep it that way: a hook
  added in a later version then arrives switched on instead of silently missing.
  `Conf.Enabled == nil` means "all mods", which is what a fresh install needs.
- Save settings on every change, not only on Play. `ui.Run` takes `remember` and
  `play` separately, the page calls `smlSave` from every handler, and the flags
  field debounces 250 ms. Somebody who ticks a box and closes the window has
  still chosen something.
- Start the host before the game. `protocol.exe` waits for the game process to
  appear. A late attach can miss a world load.
- Do not spell the game executable out anywhere but `game/exe.go`. `game.Find`
  tries `pureHD.exe`, `Sacred.exe` and `Game.exe` in that order and ignores
  case, because a copy named `sacred.exe` is the same install to Windows.
  `tools/install.ps1` carries the same three names, which is the one place they
  are written twice: PowerShell cannot read the Go list.
- The version is what says whether this is the build the addresses came from,
  never the file name. A renamed copy of the wrapper is still the wrapper, and
  the stock game would pass a name check on the second name we try.
  `game.Expected` is that version and `game.Describe` performs the comparison.
  Both live in `exe.go` with the names.
- A version mismatch is drawn as a caution and changes nothing else. Play still
  works, the mods still tick, and `game.Expected` never reaches the host. The
  loader attaching to an unknown build is the decision this repository has
  already made. The launcher must tell the player before they press the button.
  That is why the strip is
  `--warn` rather than the `--bad` red an unsupported mod gets: one of these is
  a thing that cannot work, the other is a thing nobody has checked.
- `--no-hook` is passed only when the list is non-empty. An empty value reaches
  the agent as a list containing one empty name.
- Never drop a mod from the list because it is incompatible. `mods.Loader`
  identifies the API contract and launcher release. `Loader.Refuse` measures a
  descriptor's two ranges against it: `api`, the
  contract the code was compiled for, and `loader`, the launcher releases the
  mod asked for. A descriptor with no `api` at all is refused, which is what the
  zygote does with it too. A missing `loader` is accepted because most mods have no
  opinion about the release number and should not have to invent one. An
  unsupported mod is drawn switched off, its checkbox disabled, with
  `Mod.Refusal` in red under the description, and `choice()` never puts its id
  in the enabled list whatever `launcher.json` still remembers. Keep the
  refusal visible so the author knows that the mod needs a rebuild.
- The refusal is written in Go and printed as-is. `Mod.Refusal` is a whole
  sentence naming the range the mod asked for, because that string is the thing
  somebody has to change. The page's own wording is only the fallback for a
  refusal that arrived without one.
- A JDK the launcher fetches goes in `<game>/launcher/java` and nowhere else.
  Not `%ProgramFiles%`, not `%LOCALAPPDATA%`, not a system-wide install, not a
  registry key. Uninstalling this loader is deleting the game folder, and that
  sentence stops being true the moment something is written outside it. The same
  goes for a test: everything under `java/` writes into `t.TempDir()`, and
  nothing in the suite downloads a JDK.
- Do not write down a vendor list or a version list. Both come out of the foojay
  Disco API, filtered by the rules in `Vendors` and `Versions`, so a
  distribution published after this build still appears. A hardcoded list is a
  release of ours every time somebody else ships a JDK.
- Do not trust `directly_downloadable` because it was passed as a query
  parameter. `readPackages` checks the field on every entry it keeps. A filter
  applied by somebody else is a filter that can come back wrong, and the failure
  mode is downloading a licence page and unzipping it.
- A checksum that disagrees deletes the file. Never keep a partial or mismatched
  archive under any name: the next run finds it, unpacks it, and produces a
  `java.exe` that dies on the first class it reads with nothing to say why.
- Nothing on the page may wait for the network. A WebView2 binding runs on the
  thread that pumps the window, so a binding that downloads is a window that
  freezes for four minutes with a progress bar painted on it. `java.Work` runs
  the slow half in a goroutine and the page polls `smlJava` every 200 ms.
- When the launcher finds Java, `--java` is passed on Play, not only after a
  download. With no Java path, the flag is omitted. The host then looks first
  in `<install>/java/bin/java.exe`, followed by `JAVA_HOME` and whatever `java`
  means on PATH.
- `mods.API` has to move with `Api.VERSION` in coderpack and `Verifier.API` in
  the build repository. There is no shared source: this one is read without a
  JVM. Coderpack's CI checks out this repository and the plugin and fails when
  the three disagree, so forgetting one is a red build there rather than a mod
  stamped with a major the loader refuses.
- The `pin` notation is written three times and there is no shared source
  either: `pin` here, `Ranges` in coderpack's zygote, `Ranges` in the build
  repository's linter. Each carries the same corpus of cases as its test, which
  is the specification. A case added to one belongs in all three.

## Sibling checkouts

Sibling checkouts live under `ancaria-dev/` as submodules of the workspace.
None is required for an isolated launcher build. Missing `protocol` and
`coderpack` checkouts are replaced by their pinned release assets. A missing
`mappings` checkout makes `addr.py` use its own registry fallback when
`coderpack` is built from source.

- `protocol`: the Rust host, `target/release/protocol.exe`. Takes `--enable`,
  `--no-hook` (both comma separated) and `--java`, the JDK it starts Coderpack
  with.
- `coderpack`: the Java side (`api.jar`, `zygote.jar`) and the agent JavaScript
  under `agent/src`. Also owns `tools/addr.py`.
- `mappings`: the address registry `addr.py` reads. Optional even on the
  from-source path: `build.ps1` passes `-Mappings` only when that checkout has
  a `mappings.json`, and with no argument `addr.py` falls back to downloading
  the registry. A downloaded `agent.zip` already has the table inside.

No sibling uses this repository as a build dependency. Launcher CI checks out
none of the siblings and runs
`pwsh tools/build.ps1 -Protocol none -Coderpack none`, so the download path is
exercised on pull requests, manual dispatches, and pushes to `master`.
Coderpack CI does check out launcher and build to verify that `mods.API`,
`Api.VERSION`, and `Verifier.API` agree.

## Gotchas

- `game.Version` reads the numbers in `VS_FIXEDFILEINFO`, not the `FileVersion`
  string next to them. The string is what the Properties dialog shows and it is
  useless here: the wrapper spells it "2.28" and the stock game "2.0", both
  call themselves Sacred, and both name `Sacred.exe` as their original file. The
  numbers are 2.0.2.118 against 2.0.2.28, which is the whole answer.
- `game.Expected` has to move whenever the address table does. It names the
  build `mappings` describes, and coderpack's `agent/signatures.json` names the
  same build a second time, for the agent. There is no shared source: one is Go
  reading a file, the other is JavaScript reading a process.
- An executable with no version resource at all counts as a mismatch and gets
  the strip, worded for it. Silence would be the wrong default: it is one more
  binary nobody has confirmed these addresses against.
- The launcher writes its state to `<game>/launcher/launcher.json`. It is plain
  JSON so a human can read why a mod is not loading. A corrupt file is ignored
  rather than fatal.
- Console output looked like it needed a keypress to move. That is Windows
  QuickEdit (`0x0040`): a stray click puts the console into selection mode, the
  host's next write blocks on a full buffer, and nothing appears until Enter or
  Escape. `dontPauseOnClick` in `console.go` clears it.
- Clearing QuickEdit alone breaks scrolling instead. With `ENABLE_MOUSE_INPUT`
  (`0x0010`) still set, the wheel goes to the program rather than the console
  and the window looks frozen in a quieter way. Both bits must be cleared, and
  neither takes effect unless `ENABLE_EXTENDED_FLAGS` (`0x0080`) is set with them.
- `SetProcessDpiAwareness` returns an HRESULT, where success is zero.
  Reading it like the neighbouring BOOL calls treats a working call as a failure
  and runs the blunt system-wide fallback on top of it.
- DPI awareness must be declared before any window exists. `ui.scale` must then
  size the window in real pixels. Declaring awareness without scaling makes the
  window shrink rather than sharpen.
- The binary is built `-H=windowsgui`, so there is no console to print to.
  Startup failures go through `messageBox` in `main.go`. A plain `fmt.Println`
  is invisible.
- The host is meant to outlive one game. Under the launcher it must not:
  `Session.Wait` waits for the game process it started, sleeps 500 ms so the
  host can unload cleanly, then kills it.
- Writing into the game folder fails when Sacred Gold is under `Program Files`
  and the launcher is not elevated. `main.go` says so in the error.
- A second reason to run elevated: the host inherits this process, and Frida
  cannot attach to an elevated game from a process that is not. The symptom is
  not an error but a wait that never ends on a game the host can see.
- foojay hands out Oracle's checksum as a URL, not as a value. `checksum` comes
  back empty with `checksum_uri` pointing at a `.sha256` file beside the
  archive, so `Locate` fetches that too. Reading only the field means verifying
  nothing on the default vendor.
- Zulu and Liberica answer the same query with two packages, the second carrying
  JavaFX and a hundred megabytes with it. `javafx_bundled=false` is in the query
  for that reason.
- Some distribution and version pairs have no Windows package or require a
  browser download. They stay in the dynamic dropdown because the vendor
  filter describes acceptable OpenJDK distributions, not package availability.
  `Resolve` reports the specific case instead of failing without an explanation.
- Every vendor names the folder inside the archive differently: `jdk-25.0.4`
  from Oracle, `jdk-25.0.4.1+1` from Temurin. `Unzip` finds the single common
  root and drops it, so `Find` only ever looks at `java/bin/java.exe`.
- The zip guard is `filepath.IsLocal`, and an absolute entry name is refused
  rather than trimmed. Stripping the leading slash off `/windows/system32/...`
  would contain it by accident, which is not the same as noticing it.
- `install/` and `java/` both write into `<game>/launcher`, and neither knows
  about the other. `Unpack` skips names starting with `.` and writes only what
  is in the payload, so a JDK sitting in `launcher/java` survives a version bump
  untouched.
